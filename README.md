# immedio-line — 社内共通の面談通知

同じGoogle Workspace組織の社員が、**1つの共通URL**から利用するGoogle Apps Script Webアプリです。利用者によるシートのコピー・コマンド操作・GAS作成・個別デプロイは不要です。

## 構成

| 項目 | 内容 |
|---|---|
| 公開範囲 | 同じWorkspace組織内（`DOMAIN`） |
| 実行者 | アクセスした社員本人（`USER_ACCESSING`） |
| アプリ側の許可ドメイン | 管理者の`WORKSPACE_DOMAINS`設定。今回の値は**`techbiz.com`** |
| 設定・LINEトークン・同期状態 | 社員ごとのUserProperties |
| 監視 | 社員本人が作成したカレンダー変更トリガー＋5分間隔の復旧確認 |
| 履歴 | 初回の設定保存時、社員本人のDriveへ専用スプレッドシートを自動作成 |
| 排他制御 | 社員ごとのUserLock。別社員の操作を共通ロックで止めない |

履歴シートは裏側の保存先です。設定と稼働状態はWeb画面で操作し、通常シートを開く必要はありません。GASからファイルを他人へ共有する処理はありません。

ブラウザやPCを閉じても監視します。ただし、変更発生からの即時実行・固定時間内の配信は保証しません。

## 社員の操作

1. 管理者から案内された共通URLを、会社のGoogleアカウントで開く。
2. Googleの権限確認を承認する。
3. 表示中のログインアカウントを確認し、カレンダーIDと接頭辞を保存する。
4. LINEの通知先・アクセストークンを登録する。
5. テスト送信して、LINEアプリへの到着を確認する。
6. 「監視を開始・更新」を実行する。

初回の**有効な設定の保存時**に本人のDriveへ履歴用ファイルを作ります。ページを開いたり状態を更新しただけでは作成しません。LINE設定を先に保存した場合も同様に初期化します。繰り返し保存しても同じファイルを使用します。

### カレンダー設定

- 自分のメインカレンダー：`primary`。
- 共有カレンダー：カレンダーIDを指定。本人の閲覧権限が必要です。
- 接頭辞：例`【面談】`。先頭文字列を完全一致で判定し、空白もそのまま扱います。

共有カレンダーIDはGoogleカレンダーの「設定 → 対象カレンダー → カレンダーの統合」で確認します。

設定の**保存と監視への適用は別**です。カレンダー・接頭辞を保存後、「監視を開始・更新」で適用してください。監視対象の変更や停止後の再開では初期同期し、それ以前の予定は通知しません。同じ設定の更新では開始基準と同期トークンを維持し、トリガーを再設定します。

### LINE接続

- 通知先の種類：個人／グループ。
- 通知先ID：個人は`U`、グループは`C`で始まる33文字。
- チャネルアクセストークン：LINE Messaging APIで発行したもの。

LINE公式アカウントを用意し、**Official Account Manager → 設定 → Messaging API**で利用を有効にします。その後、**LINE Developers → プロバイダー → 対応するMessaging APIチャネル**を開きます。

- 自分のID：「チャネル基本設定 → あなたのユーザーID」。プロバイダーID・チャネルID・友だち検索用LINE IDとは別です。表示されない場合はビジネスIDとLINEアカウントの連携を確認します。
- トークン：「Messaging API設定 → チャネルアクセストークン（長期）→ 発行」。Web画面へ直接入力します。
- 自分のLINEで公式アカウントを友だち追加してください。
- 種類を切り替えると入力欄が「Messaging API User ID」／「Messaging API Group ID」に変わり、取得手順も切り替わります。同じ画面内では種類別に入力値を保持し、元の種類へ戻すとそのIDを復元します。未保存の別種類の入力はページ再読込では保持しません。グループ用ヘルプには参加許可・招待・管理されたWebhook受信先の準備・署名検証済みの`source.groupId`取得・トークン登録・保存・テスト送信の手順があります。グループでも同じ公式アカウントのトークンが必要です。ID取得用Webhookは本アプリに含みません。

トークンは社員ごとのUserPropertiesに保存します。ページ表示時に認証済みの本人の値を取得し、パスワード欄へマスク表示します。目のアイコンは表示／非表示だけを切り替え、どちらの状態でもそのまま編集できます。非表示・画面切り替え・保存時に入力値を自動消去しません。空欄で保存すると登録トークンを空で上書きし、通知・テスト送信には再登録が必要です。カレンダー／LINEそれぞれの保存ボタンは、変更があり、形式チェックを通過した場合のみ有効です（初回未保存の設定は保存可能）。画面側でIDの種類・33文字の16進数形式、トークンの長さ・制御文字、カレンダーID・プレフィックスの必須と長さをチェックし、サーバー側でも検証します。IDやトークンの実際の有効性・アクセス権限は監視開始やテスト送信で確認してください。編集中の変更は状態更新や保存結果の再取得で上書きしません。ブラウザの永続保存領域やログへは保存しません。通知先・トークンの変更にデプロイやトリガーの登録し直しは不要です。

未試行の通知は新しい宛先を使用します。送信試行済みで結果が不明な分は、重複や誤送信を避けるため`REVIEW`として保留します。

テスト通知もLINEの送信枠を消費します。API受付と到着は別なので、LINEアプリ側でも確認してください。LINE Notifyは使用しません。

### 状態・停止

Web画面で、自分のカレンダー変更／復旧トリガー、最終確認、待機・要確認件数を確認できます。「監視を停止」は**自分の監視用トリガーだけ**を削除し、他社員や無関係な関数のトリガーは操作しません。

## 管理者の初回公開

**既存の個人用GASへ上書きせず、新しい社内共通の独立型GASを用意する方法を推奨します。** 旧ユーザーのトークンやトリガーを共通サービスへ混ぜないためです。

1. `techbiz.com`の会社アカウントで新しいGASプロジェクトを作成する。
2. 開発者がこのソースと`appsscript.json`を反映する。
3. **プロジェクトの設定 → スクリプト プロパティ**に次を登録する。

   | プロパティ | 値 |
   |---|---|
   | `WORKSPACE_DOMAINS` | `techbiz.com` |

   この項目は非秘密の共通アクセス設定です。**社員のLINEトークンや宛先をScriptPropertiesへ登録しないでください。** 未設定・不正な設定では社員を含めてアクセス拒否します。将来複数の会社ドメインを許可する場合はカンマ区切りで明示し、管理者が審査してください。末尾一致ではなくメールドメインの完全一致です。

4. 「デプロイ → 新しいデプロイ → ウェブアプリ」で以下を設定する。

   | 項目 | 必須の設定 |
   |---|---|
   | 次のユーザーとして実行 | **ウェブアプリケーションにアクセスしているユーザー** |
   | アクセスできるユーザー | **同じWorkspace組織内**（会社名を含む選択肢の場合あり） |

5. デプロイし、発行された`/exec`のURLを保存する。
6. 管理者と別の社員の2アカウントで、後述の実環境テストを実施する。
7. 確認後に共通URLだけを社員へ案内する。社員へGASプロジェクトの編集権限は配布しない。

**「自分として実行」のまま公開範囲だけ広げてはいけません。** アクセス者と実行者が異なるブラウザ操作はコードでも拒否します。一般公開・匿名公開は使用しません。会社の管理ポリシーによりWebアプリ利用やOAuthの管理者承認が必要になる場合があります。

Advanced Calendar Serviceはマニフェストで有効化しています。標準のCloudプロジェクトを使用する場合は対応するCalendar APIも有効にしてください。組織のOAuth運用ルールに応じ、管理者が標準Cloudプロジェクトと内部向けの認証設定を用意します。

### 更新

開発者がコードを更新し、Webアプリのデプロイ管理で**新バージョン**を選択して更新します。`clasp push`だけでは、すでに公開した`/exec`の画面は新しくなりません。

時間／カレンダートリガーはプロジェクトの現在のコードを実行するため、コード反映後はWebの公開バージョンだけでなく監視処理にも影響します。更新は互換性テストと手順を用意して行ってください。

## 個人用版からの移行

- 旧個人用版で監視を停止してから、新しい共通URLへ移行してください。両方動かすと別サービスとして二重通知されます。
- 旧ScriptPropertiesのLINEトークン・設定・既存履歴シートは、**共通版へ自動移行しません**。各社員が自分の設定を登録し、専用の履歴ファイルを作成します。
- 旧シートや旧GASを自動削除しません。
- 共通版の開始前の予定・移行で停止していた間の予定は通知対象外です。

## 送信・重複防止の仕様

- 初回検知時点の件名と、監視開始後の`created`日時で新規予定を判定します。既存予定の編集を新規追加として通知しません。
- 不一致の予定も判定済みとして記録し、後から接頭辞が追加された場合の誤通知を防ぎます。初回検知前の件名変更は復元できません。
- 繰り返し予定はシリーズ本体を1回判定し、個別回・例外回は対象外です。招待・インポート予定の作成日時は、自分のカレンダーに追加された時刻と異なる場合があります。
- 通知は件名・日本時間の開始／終了日時・ミーティングURL（設定されている場合）・メモ（予定の説明欄）・カレンダーへのリンクです。場所・参加者は送りません。
- 日時は`10-25(日) 18:30〜19:00`形式です。日をまたぐ場合は終了日も表示し、終日予定は実際に含まれる日付の範囲を表示します。
- ミーティングURLは会議情報のビデオURLまたはGoogle Meetリンクから取得します。メモのHTMLは改行・リンクを残してテキスト化します。長い通知は文字数上限内で省略表示します。
- 差分同期はページをすべて取得し、履歴を保存してから同期トークンを進めます。期限切れ時の全件同期でも開始基準と履歴を維持します。
- カレンダー同期に失敗しても、保存済みのLINE通知は送信を試みます。
- 送信前に本文・宛先・再試行キー・初回試行時刻を保存します。通信結果不明や一時障害では同じ内容で再試行し、初回試行から23時間を超えた分は自動送信せず要確認にします。
- 送信待ちの本文は最初に登録した内容です。待機中の予定変更を追従する変更通知機能ではありません。
- 1回の処理で最大20件の送信を試みます。全件同期は40ページ／約2分で打ち切ります。
- 履歴は自動削除しません。肥大化時は本人が停止して保守してください。稼働中の履歴削除・編集は重複防止と再試行を壊します。
- Google／LINEの割当上限・障害の影響を受けます。即時配信・厳密な1回配信・端末への到着保証はありません。

履歴状態：`PENDING`（待機）、`SENT`（API受付）、`IGNORED`（対象外）、`CANCELLED`（送信前の削除）、`SKIPPED`（設定切替で中止）、`BLOCKED`（拒否）、`REVIEW`（結果不明等で人の確認が必要）。BLOCKED／REVIEWの自動一括再送は行いません。

## データと権限の境界

- 社員間の設定・トークン・ファイルID・同期状態はUserPropertiesで分離します。リクエストに他人のメールアドレス・ファイルIDを指定して切り替える機能はありません。
- 本人の履歴ファイルだけを保存済みIDで開きます。保存先が見つからない／権限がない場合に、勝手に代わりの空ファイルを作りません。
- **履歴用シートにLINEトークンは保存しません。** 待機中の本文・予定ID・通知先は記録します。API受付済みの本文は消去します。社員自身や組織管理者のDrive管理権限は別です。
- アプリは履歴ファイルの共有権限を追加・変更しません。社員が自分で共有した場合の閲覧範囲はDrive側の設定に従います。
- **GASのコード編集者は信頼する管理者に限定**します。UserPropertiesは一般社員間を分離する仕組みで、悪意ある共有アプリのコード変更や組織管理者から秘密にする仕組みではありません。
- スプレッドシートの読み書き、カレンダー読み取り、トリガー管理、外部通信、メールアドレス確認のOAuth権限を使います。カレンダーの編集処理はありません。
- 社内の件名・日時をLINEへ送ることについて、会社の外部サービス利用ルールを確認してください。

## 開発・検証

```bash
mise install
npm test
npm run package
```

ZIPは開発者向けのソース配布物です。一般社員には共通Web URLを配布します。Node標準機能のみを使い、ZIP生成にはmacOS／Linuxの`zip`が必要です。開発者用`.clasp.json`は公開先GASを指定し、`.claspignore`でソースのアップロード範囲を制限します。

```bash
clasp show-file-status
clasp push
```

`push`は接続先のソース全体を置き換えます。会社アカウント・接続先IDを確認してください。Google認証情報、ユーザー設定、トークン、`.clasp.json`、`.clasprc.json`はソース配布に含めません。

### push＋既存デプロイ更新をまとめる

プロジェクト直下の`.env`に、既存WebデプロイのIDを保存します（雛形は`.env.example`）。既存の`.env`がある場合は上書きせず、この項目を追加してください。

```dotenv
CLASP_DEPLOYMENT_ID=既存のデプロイID
```

デプロイIDはGASの「デプロイ → デプロイを管理」で取得します。スクリプトIDやWeb URLではありません。`.env`はGitとGASへのアップロード対象外です。環境変数にも同名がある場合は環境変数を優先します。

```bash
# 操作内容だけを確認。ネットワークアクセス・push・公開はしません
npm run deploy -- --dry-run

# 接続先に既存デプロイがあるか確認 → push → 同じIDで新バージョン → 更新結果を再取得
npm run deploy

# 変更内容をデプロイの説明に残す場合
npm run deploy -- -m "トークン表示切替・カレンダーIDヘルプ追加"
```

URLを維持するため、デプロイの新規作成は行いません。IDの未設定・接続先違い・push失敗時には更新を中止します。push後にデプロイ更新が失敗した場合、ソース（トリガー実行分）は更新済みでもWeb版は旧バージョンのままになる可能性があります。エラーを解消して再実行してください。更新後のID・バージョン・説明の再取得が一致した場合のみ成功とします。公開範囲・実行者は既存デプロイの設定を使用するため、初回は管理画面で組織内／アクセスしているユーザーとして設定してください。

### 実環境の受入確認（公開前に必要）

1. `techbiz.com`の別々の2人が同じURLを開き、本人権限で承認できる。
2. 初回表示だけではファイルやトリガーが作成されない。
3. 各人の保存で各人のDriveへ別ファイルが作成され、再保存で増殖しない。
4. A/Bの設定・トークン・履歴・キュー・開始／停止が混ざらない。
5. A/Bの予定追加がそれぞれの登録LINEへ通知され、同時変更でも重複しない。
6. 一方の停止・設定エラー・一時送信失敗が他方に影響しない。
7. 社外アカウントと未認証アクセスが拒否される。
8. Webデプロイが`DOMAIN / USER_ACCESSING`であることを管理画面でも確認する。

ローカルのサービスダブルによる2ユーザーテストは、実際のGoogleアカウント間の認可・実トリガー発火・LINE到着を確認したことにはなりません。実環境未確認の項目は未確認として扱ってください。
