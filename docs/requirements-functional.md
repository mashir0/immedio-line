## 1. 目的

Googleカレンダーに指定の接頭辞が付いた新規予定が追加された際、社員が指定したLINE個人トークまたはグループへ通知する。社員ごとのGAS作成・シートコピー・CLI操作を不要とし、共通Web画面で導入・設定・監視を完結させる。

## 2. 対象範囲

### 対象
- 同じGoogle Workspace組織の社員による利用。許可ドメインは`techbiz.com`。
- 各社員のカレンダー設定、LINE設定、監視開始・停止、テスト送信、状態確認。
- 社員別の設定保存、履歴・送信キュー、差分同期、再試行と重複抑制。
- 開発者向けローカル検証、ソース配布、既存Webデプロイの更新。

### 現時点の対象外・非保証
- 社外・匿名向けサービス、一般社員へのGAS編集権限の配布。
- Calendar予定の作成・変更、既存予定の編集通知、停止期間の予定の遡及通知。
- 繰り返し予定の各回通知、複数カレンダー／複数送信先の同時設定。
- 即時配信・固定遅延・厳密な一度だけの配信・LINE端末到着の保証。
- LINE Notify、受信メッセージへの自動応答。
- グループID取得用Webhookとその確認画面は現行機能に含まれない。追加候補として別途整理する。

## 3. 利用者・役割・段階

| 役割 | 操作・責任 |
|---|---|
| 社員 | 共通URLを開き、会社Googleアカウントで承認。本人のカレンダー／LINEを設定・保存・テストし監視を開始する。 |
| 管理者・開発者 | 共通GAS作成、組織設定、公開、コード更新、編集権限管理、障害対応を行う。 |
| LINE側の管理担当 | 対応する公式アカウントとチャネルの準備、友だち追加・グループ参加許可、トークン管理を行う。共有／社員別のチャネル運用はU-03参照。 |

- 段階1：現行の共通Webアプリ。グループ宛ては外部で取得済みのGroup IDを入力する。チャネルアクセストークンも社員が個別に入力する。
- 段階2【方針決定・未実装】：LINE送信先（User ID／Group ID）の取得・登録とチャネルアクセストークンの管理を、Web UIからLINE bot側の操作へ移行する。全社員が単一の共有LINE公式アカウント（1チャネル）を使う前提とし、社員によるトークン個別入力は廃止する。Webhook受信先の設置方式（U-01）確定後に着手する。

## 4. 構成・データ境界

```text
社員ブラウザ → 組織限定GAS Webアプリ（社員本人として実行）
                        ├─ 社員別UserProperties / UserLock
                        ├─ 社員本人のDrive：履歴・送信キュー
                        ├─ Calendar API：予定の読み取り・差分同期
                        └─ LINE Messaging API：個人／グループへ送信

段階2（方針決定・未実装）：LINE → 署名検証付きWebhook受信先 → bot操作（友だち登録→グループ招待→ID取得ボタン）→ 個別チャットへGroup ID送信 → 社員が登録
                  ※ 現行の組織限定Web URLをそのまま公開Webhookにしない。Webhook受信先は既存とは別の新規GASデプロイ（匿名アクセス可）を採用する。呼び出し頻度が低いため、GASの実行時間・同時実行数・日次クォータの制約は許容する前提とする。
```

| 保存先・境界 | 保存内容・扱い |
|---|---|
| ScriptProperties | 非秘密の許可ドメイン設定`WORKSPACE_DOMAINS`。 |
| 社員別UserProperties | 設定、LINEトークン、宛先、履歴ファイルID、監視の適用状態、同期位置、状態表示情報。 |
| 社員本人の履歴シート | 予定の判定情報、待機通知本文、再試行キー、試行時刻、送信先、API受付時刻。LINEトークンは保存しない。 |
| 社員ブラウザ | 本人の保存済みトークンを初回取得してマスク表示する。マスクは暗号化ではない。永続ストレージへの保存はしない。 |
| LINE | 件名・日時・会議URL・メモ・予定リンクを送信する。社外サービスへの情報送信となる。 |

段階2移行後は、チャネルアクセストークンはスクリプト側（共有チャネル）で一元管理し、社員別UserPropertiesへの個別保存は不要になる想定。送信先（User ID／Group ID）はbot経由で取得した値を本人がWeb UIへ登録する形を維持する。

履歴は自動共有しない。Google上の本人・管理者の権限は別途適用される。GASコード編集者は信頼境界内とし、悪意あるコード改変からUserPropertiesを保護できるとは扱わない。OAuth権限はCalendar読み取り、Sheets、トリガー管理、外部通信、本人メール確認を使用する。実際の許可範囲はmanifestと承認画面で確認する。

## 7. 通知判定・信頼性の詳細

1. 開始時に基準時刻を記録し、既存予定をベースライン化する。同じ設定の更新では基準・同期位置を維持する。
2. 監視開始後の`created`、初回検知時の件名、既処理情報により判定する。招待・インポートでは作成時刻とカレンダー追加時刻が一致しない場合がある。
3. 差分の全ページ取得と履歴の永続化が成功するまで同期位置を進めない。Calendarの同期失効時も開始基準を維持する。
4. 通知前に宛先・本文・再試行キー・初回試行時刻を永続化する。同じキーでは同じ宛先・本文を使う。
5. 通信結果不明・一時障害は再試行する。初回試行から23時間を超えたものは自動再送しない。宛先・トークン変更時の試行済み保留分も要確認にする。
6. `PENDING / SENT / IGNORED / CANCELLED / SKIPPED / BLOCKED / REVIEW`で状態を管理する。BLOCKED・REVIEWを無条件に一括再送しない。
7. 通知本文は待機登録時点の内容とする。送信受付後は本文を消去する。
8. 現行実装は1処理20件または約2分、Calendar取得は40ページまたは約2分で制限する。サービスの割当・処理件数に依存するため遅延のSLAは設けない。
9. 履歴の自動削除は未実装。保存期間とアーカイブ方針はU-05で決定し、未解決通知や重複抑制を壊す削除はしない。

## 9. セキュリティ要件・制約

- SQL/JDBCを使用しない。SQLインジェクションの対象クエリは現構成にないが、これを全体の安全性の保証に置き換えない。
- 動的表示は`textContent`／`value`で扱い、任意入力をHTML・スクリプトとして実行しない。メモのテキスト化処理をHTMLサニタイザーとして再利用しない。
- Web APIへの直接呼出しでも本人・組織・入力検証を必須とする。画面側の検証だけに依存しない。
- LINE送信は固定のHTTPSエンドポイント、JSON本文、リダイレクト無効を使用する。ローカルのデプロイはシェル文字列でなく引数配列で実行する。
- 履歴への数式注入について、現通知本文は固定文、キーは生成した接頭部から始まる。将来、任意文字列をセル先頭へ書く場合は明示的な数式無効化またはRAW書込を別途検討する。文字列書式だけで全ケースの安全を保証しない。
- トークンのブラウザ取得は合意済み仕様。侵害された端末・拡張機能、悪意あるGAS編集者からの完全秘匿はできない。
- 現時点の確認はコードレビュー・ローカルテスト。公開アプリへの侵入テストや第三者監査の完了は宣言しない。

## 10. 開発・更新要件

- Node/npmはプロジェクトのmise設定で管理する。社員へのインストールは不要。
- `npm test`で自動テスト、`npm run package`で開発者用ZIPを生成する。
- `.env`の`CLASP_DEPLOYMENT_ID`を使い、`npm run deploy -- -m "変更内容"`で既存デプロイを更新する。
- `npm run deploy -- --dry-run`は操作計画のみ。公開前の接続確認や権限確認を代替しない。
- `clasp push`はトリガー側の現行コードへ影響する。Webの`/exec`はバージョン更新も必要。新規デプロイ作成によるURL変更は通常更新では行わない。
- `.env`、認証情報、接続先ファイル、依存関係、テスト等をGASアップロード・秘密設定の配布対象から除外する。
- 本書作成では実コードの変更・commit・push・公開はしない。
